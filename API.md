# Мобильный API UnderCtrl

После сканирования QR приложение входит в аккаунт координатора, получает токен сессии и может загрузить уведомления. Push включается отдельным запросом и доступен устройствам Firebase-проекта [underctrl-d087a](https://console.firebase.google.com/project/underctrl-d087a/overview).

**Базовый адрес после выкладки** — `https://cybergarden.sosmooth.ru/api/v1`. Ниже все пути указаны относительно `/api/v1`. Для другого стенда задайте его адрес в конфигурации клиента. В запросах с телом отправляйте `Content-Type: application/json`.

## Вход после сканирования QR

1. При первом запуске сгенерируйте случайный UUID и сохраните его как `deviceId` этой установки. Сервер принимает от 1 до 128 видимых ASCII-символов без пробелов. Сохраняйте значение между запусками. Для нового устройства или переустановки создавайте новое значение.
2. В личном кабинете координатор нажимает **«Подключить телефон»**. Кабинет вызывает `POST /mobile/pairings`. Сервер отвечает `201 {"code":"<одноразовый код>","expiresAt":"<время UTC>"}`. QR содержит ровно строку `code`. Код действует пять минут. Запрос нового кода заменяет предыдущий код этого пользователя.
3. Отправьте отсканированный код и свой `deviceId` на `POST /mobile/session`. Для Android поле `platform` можно опустить. Веб-клиент передаёт `"platform":"web"`. Имя пользователя сервер определяет по коду. Регистрация Firebase для входа не требуется.

Пример запроса (вместо текста в угловых скобках подставьте действительное значение)

```http
POST /api/v1/mobile/session
Content-Type: application/json

{"code":"<полный текст QR>","deviceId":"ec14a7dc-4627-4a1c-91fc-985123882b77"}
```

Ответ `201 Created`

```json
{
  "token": "<токен мобильной сессии>",
  "tokenType": "Bearer",
  "deviceId": "ec14a7dc-4627-4a1c-91fc-985123882b77",
  "user": {"login": "shift-a", "displayName": "Анна"}
}
```

Сохраните `token` в защищённом хранилище приложения. Для следующих запросов отправляйте `Authorization: Bearer <token>`. Сервер возвращает открытое значение токена только при входе. Сессия действует до выхода, отзыва устройства владельцем, отключения аккаунта или повторного входа той же установки с новым QR. Если ответ на вход потерялся, получите новый QR и повторите запрос с тем же `deviceId`: сервер выдаст новый токен и сохранит привязку Firebase этой установки.

## Маршруты для приложения

| Метод и путь | Для чего | Результат |
|---|---|---|
| `POST /mobile/session` | Обменять `{code,deviceId,platform?}` на сессию | `201 {token,tokenType,deviceId,user:{login,displayName}}` |
| `GET /mobile/session` | Проверить сохранённый Bearer и получить профиль | `200 {deviceId,user:{login,displayName}}` |
| `GET /mobile/notifications` | Загрузить журнал уведомлений панели с отметками чтения своего аккаунта | `200 {items,nextCursor,unreadCount}`. `limit` по умолчанию 50 (1–200), для следующей страницы передайте `cursor=nextCursor`. Пустой журнал — `{"items":[],"nextCursor":null,"unreadCount":0}`. |
| `PUT /mobile/notifications/{notification_id}/read` | Отметить уведомление прочитанным для своего аккаунта. ID берётся из `items[].id`, тело пустое. | `204`, повторный запрос также возвращает `204`. |
| `PUT /mobile/devices/current/token` | Подключить push или обновить адрес доставки Firebase | `204`, тело ответа пустое. Пример ниже. |
| `DELETE /mobile/session` | Выйти и отвязать устройство от push | `204`. Удалите локальный токен. |

У всех маршрутов в этой таблице, кроме обмена одноразового кода, авторизация по Bearer. Токен открывает мобильные маршруты для вошедшего пользователя. Каждая запись журнала содержит `id`, `type`, `title`, `body`, `createdAt`, `isRead` и `readAt`. Журнал включает типы уведомлений панели, push приходит только по `critical.raised`.

## Подключение Firebase после входа

Используйте `google-services.json` вашего Android-приложения и канал «Критические сбои». На Android 13+ запросите разрешение `POST_NOTIFICATIONS`. Когда FCM зарегистрирует приложение, передайте идентификатор в API. Для регистрации по FID используйте значение из `onRegistered` и тип `fid`. Для SDK с registration token передавайте его с типом `token`, повторяя запрос при `onNewToken`. [Настройка Firebase для Android](https://firebase.google.com/docs/cloud-messaging/android/get-started)

```http
PUT /api/v1/mobile/devices/current/token
Authorization: Bearer <токен мобильной сессии>
Content-Type: application/json

{"fcmTargetType":"fid","fcmToken":"<адрес установки из Firebase Messaging>"}
```

Ответ — `204 No Content`. Поле `fcmToken` содержит 1–2048 видимых ASCII-символов без пробелов. Указывайте тип при каждом обновлении, значение по умолчанию — `token`. При смене адреса Firebase сохраните новый адрес на сервере с тем же токеном сессии.

## Кабинет и совместимость

| Метод и путь | Кто вызывает | Результат |
|---|---|---|
| `POST /mobile/pairings` | Веб-кабинет, личная cookie-сессия | `201 {code,expiresAt}`, тело запроса пустое. |
| `GET /mobile/devices` | Веб-кабинет, личная cookie-сессия | `200 {items:[{deviceId,platform,createdAt,pushEnabled}]}`. Здесь `items[].deviceId` — серверный UUID привязки для отзыва. |
| `DELETE /mobile/devices/{deviceId}` | Владелец, личная cookie-сессия | `204` при отзыве привязки по UUID из списка кабинета. |
| `POST /mobile/devices` | Прежний клиент только для push | `{code,platform,fcmToken,fcmTargetType?}` → `201 {deviceId,deviceToken}`. Выдаёт ключ управления push. |
| `DELETE /mobile/devices/current` | Устройство с ключом push или мобильной сессией | `204`, отзывает собственную привязку. |

Обычный вход использует `POST /mobile/session`. Оба способа регистрации погашают одноразовый QR. У прежнего `deviceToken` сохраняются права на обновление адреса Firebase и удаление привязки. Уже принятый Firebase push может дойти после отзыва.

## Ошибки

| Ответ | Действие клиента |
|---|---|
| `400 VALIDATION_ERROR`, `415 UNSUPPORTED_MEDIA_TYPE` | Проверить поля JSON, формат `deviceId` и Content-Type. |
| `401 MOBILE_PAIRING_INVALID` | Получить новый QR. Код мог истечь, использоваться или быть заменён. |
| `401 MOBILE_SESSION_UNAUTHORIZED` | Показать вход по QR. Предыдущий токен сессии больше не даёт доступ к аккаунту. |
| `401 MOBILE_DEVICE_UNAUTHORIZED` | Проверить Bearer для операции с регистрацией устройства. |
| `409 MOBILE_DEVICE_IN_USE` | Установка уже привязана к другому аккаунту. Выйти из него на устройстве или отозвать привязку в прежнем кабинете. При конфликте QR остаётся действительным до истечения срока. |
| `409 FCM_TOKEN_IN_USE` | Этот адрес Firebase привязан к другому устройству. Обновить или отозвать прежнюю привязку. |
| `404 NOTIFICATION_NOT_FOUND` / `MOBILE_DEVICE_NOT_FOUND` | Обновить журнал / список устройств. |
| `503 MOBILE_ACCOUNTS_DISABLED` | Для входа на стенде требуется режим личных аккаунтов. |
| `503 MOBILE_PUSH_DISABLED` | Отправка push отключена в конфигурации стенда. В режиме личных аккаунтов вход и журнал работают отдельно. |

## Что приходит в push

Событие `critical.raised` означает переход в активный P1. В источнике это `priorityId = 4` и состояние `Assigned`, `WorkInProgress` или `Research`. Пуш появится для нового активного P1, повышения до P1 или повторного открытия. Загрузка исходного архива, повтор того же импорта, обычное редактирование P1 и закрытие сами по себе пуша не создают. Новая привязка получает события, возникшие после подключения.

Android получает **data-сообщение высокого приоритета**. В `FirebaseMessagingService.onMessageReceived` сразу покажите системное уведомление с `data.title` и `data.body`. Для `NotificationManager.notify(tag, id, notification)` можно использовать `notificationId` как строковый `tag` и постоянный числовой `id`. Тогда новый инцидент создаст отдельную карточку, а повтор доставки обновит ту же. [Получение сообщений FCM](https://firebase.google.com/docs/cloud-messaging/android/receive)

Пример `RemoteMessage.data`. Все значения — строки.

```json
{
  "type": "critical.raised",
  "notificationId": "42",
  "incidentId": "INC123",
  "sysId": "001",
  "title": "Критический сбой",
  "body": "Инцидент INC123"
}
```

Считайте `notificationId` ключом дедупликации. Если исходный идентификатор превышает 256 байт, соответствующее поле `incidentId` или `sysId` пустое. Бэкенд хранит задания в PostgreSQL и повторяет временно неудачные отправки в пределах часа с момента события. Доставка зависит от Firebase, сети и разрешений устройства.

## Веб-приложение для iPhone

При входе через `POST /mobile/session` передайте `platform: "web"`, затем зарегистрируйте адрес FCM отдельным запросом. Для веб-пушей нужны HTTPS, регистрация в FCM через service worker и публичный VAPID-ключ того же Firebase-проекта. Сервер отправляет заголовок и текст в `webpush.notification`, а также `data`. При автоматическом показе SDK не создавайте вторую карточку в обработчике. На iOS 16.4+ пользователь добавляет веб-приложение на домашний экран и выдаёт разрешение после нажатия кнопки. [Firebase Web](https://firebase.google.com/docs/cloud-messaging/web/get-started) · [WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

## Проверка на устройстве

На тестовом стенде выполните исходный импорт, подключите телефон, сверните приложение и повысьте приоритет одного активного тестового инцидента до 4. Должна появиться одна карточка с номером инцидента. Повторите тот же импорт, затем отключите телефон из кабинета и создайте ещё один активный P1. Новая карточка после отключения появляться не должна.
